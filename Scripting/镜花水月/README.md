# 镜花水月

## 用途

抖音作品浏览器，支持查看用户作品、收藏和历史，解析无水印视频、图文与动图，并提供下载、保存和分享。

## 首次使用

导入并运行脚本。
按页面提示输入或打开抖音用户、作品链接。
在作品详情中选择视频、图文或动图资源。
解析完成后保存到相册或通过系统分享。

## 注意事项

登录信息、Cookie 和作品内容可能涉及隐私及平台限制。请仅处理你有权访问和保存的内容，并留意接口变化。

### 1.0.21（2026-10-12）

下载链提速：去掉两个「白跑的往返」（不新增任何请求，只是复用已有的）。

| 之前 | 现在 |
|---|---|
| 下载前先发 **HEAD** 探文件大小 | 直接用选档探测时 `Content-Range` 里的**总大小**（**省 1 次往返**） |
| 探测取的 **128KB 文件头丢掉重下** | 直接当作**第一块**（**再省 1 次往返**） |
| 每次导出都重新请求详情 | 详情加 **60 秒缓存**（反复导出同一作品免请求） |
| ratio 探测试 1440/1080/720 × 2 主机（最多 6 次） | 只试**目标值 + 1080 保底**（服务端会自动下调） |

**实测（9MB / 1440p 作品）**：
```
① 详情请求 364ms   ② 探测(含拿总大小+首块) 241ms   ③ 下载 2991ms (3.0MB/s)
  发 HEAD = false ✅   首块用探测头 = true(131072B) ✅
  完整性：9,474,714 == 9,474,714 ✅
  ffprobe：aac + hevc 1440×2560，duration 99.7s ✅
```
- 下载本体未改：仍是官方 CDN 直连 + 4MB 分块 + 单块重试 3 次

### 1.0.14（2026-10-12）

作品页不再每次进入就重新加载。

- **之前**：`useEffect(..., [isActive])` 导致每次标签页被激活、看完作品返回时都**全量重新拉取**（刷屏 + 浪费流量）
- **现在**：列表存在**模块级缓存** `worksCache` 里（含 uid / 列表 / 游标 / 是否还有更多 / 作者信息）
  - 切标签页、进详情返回、组件重挂载→**直接复用缓存，不再请求**
  - **只有**「切换用户」（右上角头像切换 或 设置页切换）与「右上角手动刷新」会重载
  - 首次进入（无缓存）仍会自动加载；缓存按 uid 校验，不会串到别人的列表

### 1.0.11（2026-10-12）

确保「观看 + 保存」两侧都是该作品的可达最高画质。

- **实测数据（只读 128KB 文件头解析）**：
  - 2K/1440p 本身就是**标准编码**：`play_addr` = `hvc1 1440×2560`（9.04–15.42MB）、`hvc1 2560×1440`（154.59MB）→ 脚本会直接选它
  - `play` 接口的 `ratio` 参数**最高只到 1080p**（请求 2160p/1440p/1080p 返回同一份 1080×1920）→ 1080 只是「自研编码档的补救上限」，不是脚本上限
  - 移动端免签详情里**没有任何 HDR / 杜比视界标记**（`HDR_type` 为空、`is_source_HDR=0`），该通道拿不到 DV
- **改正**：观看（播放/回退）也保证不降画质 —— 作品最高档是自研编码时，`play_url` 改用 `play` 接口同分辨率正码，不再只给 720p
- **诊断更明确**：仍是**一行**，但拿不到最高档时会写明原因，例：`画质 1080×1920 avc1（最高 1440p 档为抖音自研编码，Apple 设备无法使用）`

### 1.0.10（2026-10-12）

画质恢复：自研编码档不再只能降到 720p。

- **问题**：某些作品最高分辨率档是抖音自研编码 `bvc2`（iOS 不能解码/存相册），1.0.9 只能退到下一档（例如 1080p → 720p）
- **发现（实测）**：`/aweme/v1/play/?video_id=<uri>&ratio=1080p&line=0` 返回的是**标准 H.264** 版本：
  ```
  302 → ffprobe: codec_name=h264  width=1080  height=1920  (2,539,406 字节)
  ```
  即同一分辨率的可存可播版本是存在的，只是不在 `bit_rate[]` 里。请求的 ratio 超出现有时会被服务端自动向下裁到可用值。
- **修复**：
  1. `bit_rate[]` 里的自研编码档 **彻底剔除**，不再参与选档（iOS 用不了），也不再刷一堆「跳过」提示
  2. 需要那个分辨率时，用 play 接口的 `ratio` 参数取同分辨率的**标准编码**版本；只在这种情况下才多发一次请求
  3. 诊断信息**只留一行画质结论**（例：`画质 1080×1920 avc1`）
  - 实例：`7640663177764094713` —— 由 720×1280 恢复为 **1080×1920 avc1**
  - 原本就是最高标准档的作品（如 1440p hvc1）行为不变

### 1.0.9（2026-10-12）

修复「下载完成后 Photos 保存失败」—— 这是 1.0.7 「按短边取最大」引入的真 bug。

- **现象**：进度到「正在写入相册」后报「Photos 保存失败」，实际上**下载是成功的**（文件体积、文件头都正确）
- **真因（实测）**：抖音 `video.bit_rate[]` 里存在**自研编码档位**，文件头的视频编码是 **`bvc2`**（ByteVC1）。iOS 既没有解码器也不能存相册，`Photos.saveVideo` 直接返回 false
- **实例**（作品 7640663177764094713）：
  | 档位 | 分辨率 | 编码 | 相册 |
  |---|---|---|---|
  | `bit_rate:1080_1_2` | 1080×1920 | **bvc2** | ❌ |
  | `play_addr` / `play_addr_265` | 720×1280 | hvc1 (HEVC) | ✅ |
  | `bit_rate:720_2_2` / `720_3_2` | 720×1280 | **bvc2** | ❌ |
  | `play_addr_h264` | 576×1024 | avc1 (H.264) | ✅ |
  1.0.3 按字段名取 `play_addr_h264`（永远 H.264）所以能用；改成「按短边取最大」后取到了 bvc2 ⇒ 存不进去。
- **修复**：下载前读文件头 128KB、解析 `stsd` 里的视频轨编码，**只接受 `avc1/hvc1/hev1` 等 iOS 支持的编码**，自动降到下一个可用档位，并在诊断信息里写明跳过了什么
- **观看也一并修好**：播放只用标准编码档（`play_addr` 系列），避免自研编码黑屏/null 播放失败
- 附：API 的 `is_h265` / `format` 字段**区分不出**这类编码，只能靠读文件头

### 1.0.8（2026-10-12）

修复「点下载偶发失败」。

- **现象**：列表里某些作品点下载必定失败（「无法获取下载地址」）
- **真因（实测）**：推荐流里混进了**直播间卡片**（`aweme_type = 101`、`video_feed_tag = "直播中"`）——它没有 `video` 对象、没有图，所以播放地址为空；详情接口必然返回 `filter_reason: core_dep`（被平台过滤）。实测 14 条推荐流里 2 条是这种
- **修复**：列表解析时直接剔除直播间卡片与完全无媒体的条目（既放不了也下不了，留着只会误导）
- **提示更明确**：真遇到受限作品时报「该作品已被平台限制（core_dep），非本客户端问题」，不再是一句模糊的失败
- **下载更稳**：分块 512KB → 4MB；单块失败自动重试 3 次（不再一抖动就整包重下）；去掉大文件的双倍内存占用（改为逐块 `append`，不再「攒数组→合并」）

### 1.0.7（2026-10-12）

修复竖屏作品画质仍被降档的问题（1.0.6 没修干净）。

- **现象**：竖屏作品观看/下载仍是 576×1024
- **根因**：1.0.6 改成按 `height` 比较 1080，但**竖屏视频的 height 是长边**（1024/1920/2560），`height ≤ 1080` 会把 540p（576×1024）当成上限 ⇒ 正好选中它
- **修复**：一律用**短边** `min(宽,高)`（竖屏横屏通用，也正是「1080p/1440p」的定义），并取**最高画质**
- **观看一起修了**：列表播放地址原先直接取 `play_addr_h264`（实测多是 576p/720p），现在与下载共用同一选档逻辑
- 实测同一批作品：选中档位从 `576x1024 / 720x1280 / 1024x576` → `1080x1920 / 1440x2560`
- 若想限制体积：把 `MAX_VIDEO_SHORT_SIDE` 从 `0`（不限）改成 `1080` 即封顶 1080p

### 1.0.6（2026-10-12）

修复下载画质被降档的问题。

- **问题**：1.0.5 把作品详情切到移动端接口后，下载画质从 1080p 掉到 576p
- **根因**：取地址的逻辑按字段名硬选（`play_addr_h264` 优先），而移动端详情响应里该档位恰好是 1024x576 兼容档；真正的 1920x1080 在 `video.bit_rate[]` 的 `1080_1_2` 档
- **修复**：新增按清晰度选档 —— 优先 1920x1080；没有就取 ≤1080 中最高的；全都高于 1080 时取最小的
- 实测同一作品各档真实体积：1440p 116MB / **1080p 61.6MB（现已选用）** / 576p 97.6MB（原被误选）/ 720p 37.8MB
- 想要更高画质：把 `PREFERRED_VIDEO_HEIGHT` 改成 `1440`（写 `0` = 取最高可用）

### 1.0.5（2026-10-12）

新增「移动端免签通道」，减少对 Cookie 与网页端签名的依赖（接口可用性为真机实测结论）。

- **作品详情 / 去水印**：优先走移动端接口，免 Cookie、免 uifid、免签名，直接拿到无水印 CDN 直链（实测 77KB 响应含 4 条直链）；失败才回退原有 WebView 页面解析

- 下载地址优先选 CDN 直链（`douyinvod` / `tos`），避免选中需要重定向的 `aweme/v1/play` 接口
- 下载请求补上 `Referer: https://www.douyin.com/`

### 1.0.2（2026-10-12）

- 修复作品页 HTTP 403：抖音网页接口启用 ArgusSecurityPlugin 风控，缺 uifid 即 `403 Uifid Not Found`
- 作品列表改为本地生成 `x-secsdk-web-signature` 网页签名后请求（`md5(uifid_timestamp_SALT_query)`），纯本地计算，不依赖任何第三方服务
- 自动从已保存 Cookie（或 WebView Cookie 存储）获取 uifid
- 保留 Cookie 直连作为回退通道
