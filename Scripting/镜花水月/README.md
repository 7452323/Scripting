# 镜花水月

## 用途

抖音作品浏览器，支持查看用户作品、收藏和历史，解析无水印视频、图文与动图，并提供下载、保存和分享。

## 首次使用

导入并运行脚本。
按页面提示输入或打开抖音用户、作品链接。
在作品详情中选择视频、图文或动图资源。
解析完成后保存到相册或通过系统分享。

## 注意事项

登录信息、Cookie 和作品内容可能涉及隐私及平台限制。请仅处理你有权访问和保存的内容，并留意接口变化。

## 文件结构（1.0.23 起）

| 文件 | 作用 |
|---|---|
| `shared.tsx` | **全部业务代码**（`HomeView`/`HistoryView`/`SettingsView`/`App`、接口、选档与编码嗅探、下载…）。**无顶层副作用**，两个入口共用 |
| `index.tsx` | 独立运行入口：`Navigation.present(<App/>)` → 关闭后 `Script.exit()` |
| `home_screen_default_ui.tsx` | App 首页 Home Tab 入口：**直接渲染作品页**（历史 / 设置 在作品页顶栏） |

⚠️ `index.tsx` 顶层有 `Navigation.present` + `Script.exit` 副作用——**任何文件都不要 `import ... from "./index"`**（会直接弹窗并退出实例；首页会变成「无法渲染此视图」）。要从首页入口取组件，就 `import ... from "./shared"`。

**新增 iCloud 同步**（设置页），同时**去掉诊断页**。

### 为什么不用 CloudSharedData

官方那个 `CloudSharedData` 要求先在“设置 → iCloud 共享数据”里手动建个 store、拿 UUID 填进脚本，
对“打开开关就该能同步”来说太重。改用 **iCloud Drive 上的单文件**：

```
< iCloudDocumentsDirectory >/JingHuaShuiYue/sync.json
```

`FileManager.isiCloudEnabled` 真机实测为 true，读写正常。

### 同步内容

| 项 | 是否同步 | 说明 |
|---|---|---|
| 已保存用户 | ✅ | 按 `id` 字段级合并 |
| 观看历史 | ✅ | 按 `aweme_id` 去重，按时间降序，上限 500 |
| 当前用户 | ❌ | 各设备各自选 |
| Cookie | ❌ | 敏感，且多设备登录态互相干扰 |

### 合并规则（关键）

**双向合并，两个方向都写**：读云端 → 合并 → 写本地 Storage → 写回云端。
所以不会出现“A 设备把 B 设备新增的条目覆盖掉”。

- 用户：空字段让位；`totalFavorited/followingCount/followerCount` 取大；`savedAt` 取早（保留“首次添加”时间）
- 历史：同 `aweme_id` 取 `viewed_at` 更新的那条

单测（纯函数）实测：`[A(昵称), B(空)] × [A(空), B(昵称+粉丝12), C(新)]` →
3 个用户，A 保留昵称且 `savedAt=100`、`fans=9`，B 补全昵称且 `fans=12`，C 新增；
历史 `[1(旧),2] × [1(新),3]` → `3,1,2` 且 id=1 取新的那条。

### 触发时机

- 打开设置页：先合并一次（状态栏直接显示“已同步 · 40 个用户 / 96 条历史”）
- 保存/删除用户、新增/清空历史：2.5s 防抖后推一次
- 「立即同步」按钮：手动

真机验证：`sync.json` 已生成 **155546 B**，设置页显示“已同步 40 个用户 / 96 条历史 · 23:39”。

### 1.0.50（2026-11-02）

三个体验问题，一个根因一类修法：

**① 顶部冒出「分页只走签名通道」**

那是我 1.0.47 写的 `throw new Error("分页只走签名通道")`，被 `doLoadVideos` 的 catch 直接
`setError(err.message)` 弹到顶栏了。分页失败是**内部状态**（后台会自己重试），不该让用户看到。
→ signerOnly 抛的错误打 `silent` 标记，catch 里过滤。

**② 作品不再继续出（卡在 30 条）**

旧后台逻辑：失败→重试 1 次→仍失败就 `break`；空页直接判“到底”。
于是只要碰上一次限流/超时，列表就永久停在首屏那 30 条。
→ 改成：失败**退避重试 3 次**（4s / 8s / 12s）；空页给一次机会（连续两次空页、或
游标没前进才停）；批数上限 20 批（≈1200 条）。

**③ 每次打开等好久**

根因：首屏必须走 Python 签名，而 Python **冷启动固定 3.5–6s**；内存 listCache 只管同一次
进程，App 重开后它空了 → 每次都要白等。
→ 新增**跨进程首屏快照**（Storage `douyin_last_list`，存当前用户前 90 条 + 游标 + 昵称头像，
绑 Cookie 指纹）：

```
HomeView 初始化  → 读快照 → 直接上屏（loading 不做，不闪空）
后台             → doLoadVideos(true) 静默刷新（同号不清屏、不盖旧内容）
```

实测快照：37365 B，30 条，`has_more=true`，`total=323`，置顶在首条。
Storage 写入上限已验证（97 KB / 289 KB 均可写读，所以 37 KB 没问题）。

**偶发丢昵称/头像 + 底部一直挂「加载更多」。**

### 1.0.41（2026-11-01）

**“登录着却只显示最近 15 条”的真因：Python 串行队列被后台续拉堵满。**

实测证据（本机）：

| 探针 | 结果 |
|---|---|
| `profile/self`（现有 Cookie） | **sc=0，已登录** —— 登录态没问题 |
| `Python.run("print('hello-python')")` | **37020ms 才返回** —— 队列里排了一堆积压任务 |
| 首屏 `fetchUserPosts` | 排队 → 超 30s → 降级分享页 → **15 条** |

为什么积压：`Python.run` 是**串行队列且不能被 timeout 取消**（`timeoutFetch` 只是 race）。
1.0.40 的后台续拉每页一个 `Python.run`，用户刷新/切号时前台请求被挤到超时；
而超时后旧版还会继续重试 → 任务越堆越多（实测已经要等 37s）。

修法：

- **后台降频**：每页之间 `await sleep(800)`
- **切到别的 Tab 立即作废后台**（`onHomeTabEvent("deselected")` → `bgPullToken++`）
- **后台给前台让路**：每页开始前若 `resetInFlight` 非空就等（最多 30s）
- **超时改为 90 秒短冷却**（`markSignerSlow`），不再每次刷新都往队列里再塞一个 30s 任务；
  硬失败（非超时）仍为 5 分钟
- **后台失败不冷却签名器**（`fetchUserPostsOnce(..., { noCooldown: true })`）
- 底部提示区分两种情形：
  - 有 Cookie：「签名通道这次没成功（请求被排队或网络拖断），已临时换成分享页。点「重试」再试一次。」
  - 无 Cookie：保留「登录后可拿完整列表」

⚠️ 已积压的队列靠 Reload / 重启 App 清掉。

### 1.0.40（2026-11-01）

**切用户后自动增量补齐全部作品（后台逐页拉，不拖慢首屏）。**

需求：一次性拉 326 条要 11 页 ≈ 22s，会卡住首屏；但又不能只给首屏 30 条。

实现：

- 首屏（`doLoadVideos(true)`）只拉第一页 → 先上屏，界面立刻可滑/可播
- 首屏成功后如果 `hasMore` → 启动 `pullRestInBackground(uid, cursor, token)`：
  逐页 `fetchUserPostsOnce`（每页 ~2s），每拉一页就按 `aweme_id` 去重合并进列表，
  同步更新 `cursor / hasMore / totalCount / bgLoaded`
- footer 在 `hasMore` 时优先显示「后台加载中… 已 N 条（可以正常滑动/播放）」，
  不再显示「加载更多」按钮；后台停下后才回到手动按钮（作兜底）
- **命中缓存但上次没翻完**（退出 App / 切走中断）时，`useEffect` 里不重拉首屏，
  但会接着用 `worksCache.cursor` 继续后台补齐

并发/切换安全：

- `bgPullToken`：切号 / 刷新（reset）时自增 → 旧后台循环在下一个检查点自行退出
- `bgPullBusy` + `bgPending`：同一时间只跑一个后台循环；被撞掉的新请求记为 pending，
  旧循环退出后立刻接着跑（避免「切号后后台就不动了」）
- `Script.onHomeTabEvent("reselected")` 在后台跑时不再插手拉取

验证：逐页翻页链路已实测（p1 30 条 `more=true`、p2 `uniq=60 more=true`，游标正常推进）；
类型检查 0 错误，首屏渲染正常。

**诊断里的作品数量看着像“没拉全”。**

- **修复**：下载前读文件头 128KB、解析 `stsd` 里的视频轨编码，**只接受 `avc1/hvc1/hev1` 等 iOS 支持的编码**，自动降到下一个可用档位，并在诊断信息里写明跳过了什么
- **观看也一并修好**：播放只用标准编码档（`play_addr` 系列），避免自研编码黑屏/null 播放失败
- 附：API 的 `is_h265` / `format` 字段**区分不出**这类编码，只能靠读文件头

### 1.0.8（2026-10-12）

修复「点下载偶发失败」。

- **现象**：列表里某些作品点下载必定失败（「无法获取下载地址」）
- **真因（实测）**：推荐流里混进了**直播间卡片**（`aweme_type = 101`、`video_feed_tag = "直播中"`）——它没有 `video` 对象、没有图，所以播放地址为空；详情接口必然返回 `filter_reason: core_dep`（被平台过滤）。实测 14 条推荐流里 2 条是这种
- **修复**：列表解析时直接剔除直播间卡片与完全无媒体的条目（既放不了也下不了，留着只会误导）
- **提示更明确**：真遇到受限作品时报「该作品已被平台限制（core_dep），非本客户端问题」，不再是一句模糊的失败
- **下载更稳**：分块 512KB → 4MB；单块失败自动重试 3 次（不再一抖动就整包重下）；去掉大文件的双倍内存占用（改为逐块 `append`，不再「攒数组→合并」）

### 1.0.7（2026-10-12）

修复竖屏作品画质仍被降档的问题（1.0.6 没修干净）。

- **现象**：竖屏作品观看/下载仍是 576×1024
- **根因**：1.0.6 改成按 `height` 比较 1080，但**竖屏视频的 height 是长边**（1024/1920/2560），`height ≤ 1080` 会把 540p（576×1024）当成上限 ⇒ 正好选中它
- **修复**：一律用**短边** `min(宽,高)`（竖屏横屏通用，也正是「1080p/1440p」的定义），并取**最高画质**
- **观看一起修了**：列表播放地址原先直接取 `play_addr_h264`（实测多是 576p/720p），现在与下载共用同一选档逻辑
- 实测同一批作品：选中档位从 `576x1024 / 720x1280 / 1024x576` → `1080x1920 / 1440x2560`
- 若想限制体积：把 `MAX_VIDEO_SHORT_SIDE` 从 `0`（不限）改成 `1080` 即封顶 1080p

### 1.0.6（2026-10-12）

修复下载画质被降档的问题。

- **问题**：1.0.5 把作品详情切到移动端接口后，下载画质从 1080p 掉到 576p
- **根因**：取地址的逻辑按字段名硬选（`play_addr_h264` 优先），而移动端详情响应里该档位恰好是 1024x576 兼容档；真正的 1920x1080 在 `video.bit_rate[]` 的 `1080_1_2` 档
- **修复**：新增按清晰度选档 —— 优先 1920x1080；没有就取 ≤1080 中最高的；全都高于 1080 时取最小的
- 实测同一作品各档真实体积：1440p 116MB / **1080p 61.6MB（现已选用）** / 576p 97.6MB（原被误选）/ 720p 37.8MB
- 想要更高画质：把 `PREFERRED_VIDEO_HEIGHT` 改成 `1440`（写 `0` = 取最高可用）
