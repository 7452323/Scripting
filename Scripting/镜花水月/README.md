# 镜花水月

## 用途

抖音作品浏览器，支持查看用户作品、收藏和历史，解析无水印视频、图文与动图，并提供下载、保存和分享。

## 首次使用

导入并运行脚本。
按页面提示输入或打开抖音用户、作品链接。
在作品详情中选择视频、图文或动图资源。
解析完成后保存到相册或通过系统分享。

## 注意事项

登录信息、Cookie 和作品内容可能涉及隐私及平台限制。请仅处理你有权访问和保存的内容，并留意接口变化。

## 文件结构（1.0.23 起）

| 文件 | 作用 |
|---|---|
| `shared.tsx` | **全部业务代码**（`HomeView`/`HistoryView`/`SettingsView`/`App`、接口、选档与编码嗅探、下载…）。**无顶层副作用**，两个入口共用 |
| `index.tsx` | 独立运行入口：`Navigation.present(<App/>)` → 关闭后 `Script.exit()` |
| `home_screen_default_ui.tsx` | App 首页 Home Tab 入口：**直接渲染作品页**（历史 / 设置 在作品页顶栏） |

⚠️ `index.tsx` 顶层有 `Navigation.present` + `Script.exit` 副作用——**任何文件都不要 `import ... from "./index"`**（会直接弹窗并退出实例；首页会变成「无法渲染此视图」）。要从首页入口取组件，就 `import ... from "./shared"`。

## 版本更新

### 1.0.37（2026-10-17）

> 本节是**排查记录**（技术细节）；App 内的更新弹窗只保留「新增 / 修复」短句。

两轮全量审查（数据层 + UI 层）后修掉的问题：

第一轮（数据层/并发/缓存/通道回退）发现并修掉：

| 问题 | 后果 | 修法 |
|---|---|---|
| 切号时 `resetInFlight` 直接丢弃新请求 | 界面短暂显示上一个号的作品/昵称，要切 tab 才恢复 | 锁改成 `{uid, seq}`：同号重复请求丢弃，**换号则作废旧请求**并放行 |
| 一次排队超时就 `markSignerDead()` | 签名通道冷却 5 分钟，只剩分享页 15 条 | 只有非 `timeout` 异常才冷却；`urlopen` 超时 25s → 12s |
| 合法空页（翻到底）被当成通道失败 | 下滑到底 → 回退分享页 → `maxCursor` 被重置回 0 | `fetchUserPostsViaSigner` 返回 `ok`，空列表也当成功 |
| `lastAwemeCount` 跨用户残留 | 新号会显示「已显示 X / 共 Y」里的 Y 是上一个号的 | 首页/重置时清零 |
| 绦拉失败被 `catch { more=false }` 吞掉 | 网络失败被说成「仅自己可见」 | 记 `lastPartialError`，footer 区分红字「分页请求失败」 |
| `reselected` 用 `totalCount` 判缺口 | `aweme_count` 含私密作品 → 每次点 Home 都整轮重拉 | 改为 `hasMore` 时续拉一页 |
| `cookieSig` 在请求**完成**时计算 | 刷新途中登录 → 旧列表被标成新签名 → 之后不再重拉 | 改为请求开始时取指纹 |
| 分享页 45s 释放定时器未在取数时撤销 | 取数途中 WebView 被 dispose → 返回空 | 入口先 `clearTimeout` |
| `ensureUifid` / `resolveViaWebView` 无超时 | 验证码页会让加载一直转圈 | 各包 `timeoutFetch` |
| 切号失败时 `userInfo` 残留 | 顶部仍显示上一个号 | reset 时按 `savedUsers` 预填/清空 |

第二轮（UI/边界/资源）发现并修掉：

- `DouyinLoginView` 的 `WebViewController` 从不 `dispose` → 每次登录泄漏一个（现已加 cleanup）
- 登录保存的 Cookie 同名多条未去重 → 改为 `Map` 按 name 去重
- 登录后未清旧 `uifid` 缓存 → 加 `clearUifid()`
- **Home Tab 里从设置页返回收不到 `onHomeTabEvent`** → 登录后首页不刷新；
  改为 `SettingsView` 接 `onCookieChanged` 回调，登录/校验保存成功时直接触发重拉
- `listComplete` / `listShort` 未考虑分页失败 → 分页失败时不再谎报「已加载全部」

审查结论（未改，计作已知项）：

- `fetchViaWebView` / `chunkItems` 是死代码（无调用），保留不动（无运行影响，历史回退参考）
- `: any` 42 处：抖音 JSON 字段不稳定，用 any 是刻意选择
- 首屏耗时：`Python.run` 冷启动约 3-4s + 列表请求 1.5s + 总数 2s ≈ **5-8s**（热进程约 1.5s）；这是既有架构成本，不属 bug

### 1.0.36（2026-10-17）

**置顶作品拿不到的真正原因：首页游标写错了。**

实测账号 `81170919561`（唯优，328 条）：

| 请求 | 返回 |
|---|---|
| `max_cursor=0` | **前两条 `is_top=1`**：「早上好」(ct=1778980526 / 2026-05-08)、「谢谢你的浏览 我确实很拿得出」(ct=1737773217 / 2025-01-25)，后面才是时间降序 |
| `max_cursor=now`（1.0.30~1.0.35 用的） | 最新 30 条，**`is_top` 全是 0，置顶一条都没有** |

置顶的都是**老作品**，`max_cursor=now` 的时间窗口直接把它们跳过了。
1.0.30 当时看到「cursor=0 首条是 2025-12-03」就断定它会反向，那个结论是错的：
那次看到的是「没有置顶的账号」的普通降序，当时又没做兜底反转。

现在：

- 首页 `effCursor` = `"0"`（翻页继续用服务端回的 `max_cursor`）
- `fixOrder()` 兜底：只有整页**严格递增**才整体反转（置顶混入时不会被误判）
- 置顶卡片右上角加「`pin.fill` 置顶」角标（`is_top=1` 才显示，`allowsHitTesting={false}` 不影响点击）

回归：`fetchUserPosts(81170919561)` → 2.1s / 30 条 / 前两条 `top=1` / `has_more=true` / `total=328`。

### 1.0.35（2026-10-17）

**置顶作品又丢了 / 列表变成最旧在前。**

两个错都在「排序」上：

1. **客户端不该重排**。接口 `aweme_list` 本身就把作者置顶放在最前，但 **`is_top` 字段全是 0**（实测 8 条），
   所以 1.0.34 里那个「置顶优先 + 时间降序」实际就等于纯时间降序——置顶的老作品会被打到列表最底。
   → 现在顺序**完全以服务端为准**，只保留一个兵底：整页**严格递增**（历史 `max_cursor=0` 反向）才整体反转。
2. **反转判断写反了**（调试中自己引入的）：降序列表被判成“需要反转”→ 变成最旧在前。已修。

顺带修了一个真实的并发 bug：

- `onHomeTabEvent("selected")` 和 `useEffect([isActive])` 可能同时触发首屏重拉 → 两次 `Python.run` 在串行队列里排队
  → 后一个 30s 超时 → `markSignerDead()` → 回退分享页（条数更少）→ **把已经拿到的完整列表覆盖成残缺的**
- 修法：模块级 `resetInFlight` 互斥锁 + `loadSeq` 请求序号（旧请求的结果直接丢弃，不再 setVideos）

回归（真机）：`fetchUserPosts` 1.4s / **8 条** / `has_more=0` / 首条 = 「讨厌我吧 晚安」，顺序与服务端一致。

### 1.0.34（2026-10-17）

**两个入口列表不一致（置顶作品 / 登录后的新作品）。**

现象：首页 Tab 里置顶的两条在最前，但从脚本列表《运行脚本》打开的 App 里没有这两条。

排查（本机实测）：

| 检查 | 结果 |
|---|---|
| 签名通道拉取（登录后的 Cookie） | **返回 8 条**，`has_more=0`，前两条就是「讨厌我吧 晚安」/「镇收邪祟，荡尽魑魅」 |
| 同一条链的 `fetchUserPosts` | 1.79s / 8 条 / `totalCount=7`，顺序已是时间降序 |
| `aweme_list[i].is_top` | **全是 0**（服务端不给置顶标记），但返回顺序本身就把置顶放在最前 |
| 两个入口是否同一函数 | 是（都走 `HomeView` → `fetchUserPosts`） |

⇒ 真正的原因：**列表缓存只按“用户变了”失效，不按“登录态变了”失效**。
独立运行的 App 实例早先（Cookie 已失效时）拉的是 4 条，之后去设置页获取了 Cookie，
首页 Tab 因为 `onHomeTabEvent` 刷新成 8 条，而那个 App 实例的 `worksCache` 仍然是旧 4 条。

修法：

- `worksCache` 增加 `cookieSig`（Cookie 长度 + 首尾 8 字符的指纹，**不存完整凭据**）
- `doLoadVideos` 成功时写入指纹；`useEffect([isActive])` 里指纹不一致就强制重拉
  → 登录后从设置页切回首页（或从任何 Tab 切回）都会自动拿到全量
- 排序改成 `compareAweme()`：**置顶优先（`is_top`），其余按时间降序**。
  之前单纯按 `create_time` 降序，置顶的老作品会被排到最底，看起来就像“那几条没了”

### 1.0.30（2026-10-17）

**修复「作品只显示最早的、刷不出最新」**。

根因（实测）：

```
max_cursor=0    → 首条 2025-12-03（最旧！）  末条 2026-10-01   ❌
max_cursor=now  → 首条 2026-10-01（最新 ✅） 末条 2026-08-11
不带 max_cursor → 顺序不稳定（两次跑结果相反）
```

⇒ 作品接口把 `max_cursor=0` 当成「无上界/从头开始」，会从**最旧**开始返回；
而传**当前时间戳**才是「从最新往回」。

修法：
- 首页（cursor=0）→ 改传 `Date.now()`；翻页继续用服务端回的 `max_cursor`
- 列表再按 `create_time` **降序**排一次（服务端顺序不可靠，兼保险）
- 回归实测：第1页 23 条（首条 2026-10-01「国庆主题绘画」），第2页 30 条（2026-08-08） ✅

### 1.0.26（2026-10-14）

修复「作品页 HTTP 403」。**根因：抖音改了网页端的 Argus 签名算法**，旧通道整体失效。

**实测（真机逐条打点）**

| 通道 | 结果 |
|---|---|
| 移动端 `/aweme/v1/aweme/post/` | 200 但**空列表**（IP 级风控，换身份/主机/UA 全一样） |
| 移动端 `/aweme/v1/aweme/detail/` | 200 / 84KB ✅（IP 没被封） |
| 网页端（无 uifid） | 403 `Uifid Not Found` |
| 网页端（有 uifid、无签名） | 403 `Signature Not Found` ← **uifid 有效（320 位）** |
| 网页端（uifid + 本地 md5 签名） | **请求被服务端拖住不返回** ⇒ 签名算法已变 |

**修法：新增免签名通道（WebView + 分享页）**

- `WebView` 打开 `m.douyin.com/share/user/<sec_uid>` —— 页面**自己能签名**、会把作品渲染出来

新增「移动端免签通道」，减少对 Cookie 与网页端签名的依赖（接口可用性为真机实测结论）。

- **作品详情 / 去水印**：优先走移动端接口，免 Cookie、免 uifid、免签名，直接拿到无水印 CDN 直链（实测 77KB 响应含 4 条直链）；失败才回退原有 WebView 页面解析
- **用户信息**：先不带 Cookie 请求 iesdouyin（实测免签可用），失败才带 Cookie；shortId / 获赞 / IP 地区优先从移动端作者信息补全
- **作品列表**：新增移动端通道作为首选项，返回空或被限流时**自动回退网页端签名通道**（不改变原有稳定性）
- 技术备注：移动端接口要求 `iid` 用真实 install_id（用 device_id 顶替会返回 `status_code 2154`）；设备参数已内置实测默认值（Storage 键 `douyin_install_id` / `douyin_device_id` 可覆盖）；**不要给移动端请求带 x-gorgon/x-argus 签名**（实测带上反而返空）
